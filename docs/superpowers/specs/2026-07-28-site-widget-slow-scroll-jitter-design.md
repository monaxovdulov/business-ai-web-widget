# Дизайн: устранение дрожания при медленном скролле истории

Статус: одобрено пользователем, реализовано
Дата: 2026-07-28
Область: `packages/site-widget`

## 1. Проблема

При медленном ручном скролле истории вверх viewport возвращается вниз, из-за чего
возникает заметное дрожание.

Причина находится в `MessageScrollerController`:

1. `wheel`, `touchmove` или другое ручное действие переводит controller из
   `following-bottom` в `free-scrolling`.
2. Первый небольшой шаг вверх оставляет viewport ближе
   `SCROLL_EDGE_THRESHOLD` (`8px`) к нижней границе.
3. Следующий `scroll` event немедленно возвращает режим `following-bottom`.
4. Reconcile снова программно прокручивает viewport вниз.

Быстрый скролл обычно сразу проходит больше `8px`, поэтому дефект проявляется
прежде всего при медленном движении.

## 2. Требуемое поведение

- Любое подтверждённое ручное движение вверх сразу отключает автоследование.
- Пока пользователь движется вверх или читает историю, новые сообщения и
  изменение высоты существующих сообщений не сдвигают viewport вниз.
- Автоследование возвращается, когда пользователь сам прокрутил вниз до live
  edge либо нажал кнопку `К новым сообщениям`.
- Первичное открытие, отправка нового visitor message, turn anchor,
  программный `scrollToEnd()`, resize и `prefers-reduced-motion` продолжают
  работать как раньше.

## 3. Выбранный подход

Controller будет учитывать направление непрограммного скролла.

- Перед обработкой события сохраняется предыдущее наблюдаемое значение
  `scrollTop`.
- Непрограммное уменьшение `scrollTop` больше `SCROLL_EPSILON` считается
  движением пользователя вверх и фиксирует `free-scrolling`.
- Такой же event не может одновременно вернуть `following-bottom`, даже если
  расстояние до конца всё ещё меньше `8px`.
- Возврат к `following-bottom` разрешён только при непрограммном движении вниз
  до live edge или через явный `scrollToEnd()`.
- Программные перемещения остаются защищены существующим флагом
  `programmaticScroll`; публичные свойства, события и HTML-контракт не меняются.

Подход с уменьшением threshold не используется: он не устраняет гонку состояний
и зависит от дробных значений scroll position. Временная блокировка после
ручного действия также не используется, потому что добавляет недетерминированный
таймер.

## 4. Изменения

Основной файл:

- `packages/site-widget/src/controllers/message-scroller-controller.ts`

Тесты:

- `packages/site-widget/tests/browser/message-scroller.spec.ts`

Допустимы минимальные изменения fixture API, только если они нужны для
детерминированного воспроизведения малых scroll delta.

## 5. Проверка

Новый browser test должен:

1. Открыть историю в состоянии `following-bottom`.
2. Выполнить несколько медленных ручных шагов вверх, каждый меньше `8px`.
3. Проверить, что `scrollTop` не возвращается вниз и режим остаётся
   `free-scrolling`.
4. Добавить или увеличить сообщение и убедиться, что viewport не сдвинулся.
5. Прокрутить вручную вниз до live edge и проверить возврат
   `following-bottom`.
6. Повторить выход из live edge и проверить возврат кнопкой
   `К новым сообщениям`.

Также должны пройти существующие component, browser, typecheck и build tests.

## 6. Не входит в работу

- изменение дизайна scrollbar или кнопки `К новым сообщениям`;
- изменение размера `SCROLL_EDGE_THRESHOLD`;
- изменение backend API, истории сообщений или session storage;
- обновление других частей chat state machine;
- несвязанный рефакторинг `MessageScrollerController`.

## 7. Выпуск

После прохождения тестов:

1. Собрать новый immutable runtime в `business-ai-web-widget`.
2. Обновить vendored runtime, manifest, source commit и SHA-256 в
   `landing-granit-static`.
3. Переключить `index.html` и `catalog.html` на новый runtime.
4. Прогнать smoke-проверки лендинга и задеплоить `main` на staging.
